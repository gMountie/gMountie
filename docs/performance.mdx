# Performance

Live charts from the gMountie [Bencher](https://bencher.dev/) dashboard. Every tagged release runs the same fio-based benchmark suite against a fixed perf pod, and the results land on these plots — so what you see below is the **current** state of the codebase, not a snapshot frozen in a README.

For the *why* behind the design — readahead window, write coalescing, the dirent cache — see **[Design — Performance](./design/performance.md)**. This page is the data.

## How to read these charts

- **Each line is a benchmark.** Sequential plots show 3 file sizes × 2 I/O paths (plain and optimized) = 6 lines. Random/metadata plots show 4 KiB read + 4 KiB write side by side.
- **X axis is wall-clock time** (one point per release).
- **Y axis is what the harness measured** — MB/s for throughput, nanoseconds for latency. The unit is in the chart title.
- **Two link profiles.** `lan` = full-rate loopback. `wan` = `tc netem` shaping the loopback with realistic internet RTT and bandwidth. The split matters: gMountie's whole reason to exist is the WAN side.

The testbed (`gmountie-perf-pod`) is a single fixed machine — it gives you trend, not absolute headroom on your hardware. Run the [perf suite](https://github.com/gMountie/gMountie/tree/master/test/e2e/perf) on your own host if you want to compare against your own ceiling.

## Sequential read throughput (LAN)

The headline number. Driven by the [readahead window](./client/config.md#readahead) — chunk size × number of in-flight chunks. The `Opt` variants use the partial-consume + cross-chunk path that landed in [#0f1dd8e](https://github.com/gMountie/gMountie/commit/0f1dd8e); the gap between plain and Opt is the value of that work.

## Random 4 KiB I/O latency

Tail behaviour on small, scattered I/O. The harness tracks **central latency** per benchmark (nanoseconds), not a percentile — Bencher's threshold system uses iterative t-tests on the central tendency. For percentile breakdowns, run [`task perf:bench:fs`](https://github.com/gMountie/gMountie/blob/master/test/e2e/perf/) locally; the fio reports include p99 inline.

## What lives on the dashboard but not here

The full Bencher project has 12 plots; this page embeds 4. The others — normalized overhead (% of the min(disk,link) ceiling), WAN variants, the substrate floor (raw disk and raw network MB/s on the same pod) — are linked inline or available straight on the **[Bencher dashboard](https://bencher.dev/perf/gmountie-tfkojd8g)**.

The plot set is declared in [`scripts/perf/plots.yaml`](https://github.com/gMountie/gMountie/blob/master/scripts/perf/plots.yaml) and synced with `task perf:plots:sync`, so it's reproducible and reviewable in PRs — no clickops on the dashboard.

## Caveats

- **One testbed.** Every line on every chart is from the same machine. Use it for *trend* (did this PR slow things down?), not as a hardware-portable absolute.
- **Public, alert-only.** The Bencher project is public; CI raises an alert on regression but does not fail the build. Performance is tracked, not gated.
- **Release cadence.** Each tagged release publishes one point per benchmark per plot. Mid-PR perf work is run locally and only lands on Bencher when the PR merges and a release is cut. See [`design/performance.md`](./design/performance.md) for the release-gated flow.
