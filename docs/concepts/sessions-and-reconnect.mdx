# Sessions & reconnect

**The internet drops packets, NATs rebind, and ISPs reassign IPs. gMountie is built to ride that out: data-path operations retry transient gRPC failures on a bounded budget, the keepalive/session stream reconnects in the background, and open file handles survive a short outage.** Three mechanisms cooperate to make that work.

## 1 · Keepalive — detecting a dead path quickly

gRPC HTTP/2 keepalive pings run in **both directions**:

- The **client** pings the server every `rpc.keepalive.time` (default 30 s) and waits up to `rpc.keepalive.timeout` (default 10 s) for an ACK.
- The **server** does the symmetric thing on its side using `server.keepalive.time` / `timeout`.

If the ACK doesn't come back, the connection is torn down and the next RPC observes `Unavailable`. Default ~40 s end-to-end (30 s interval + 10 s timeout). That's much faster than the kernel's default TCP timeouts (minutes), so a dead path surfaces while the user is still at their terminal.

```yaml
# client
rpc:
  keepalive:
    time: 15s        # tighter detection
    timeout: 5s
    permit_without_stream: true

# server
server:
  keepalive:
    time: 15s
    timeout: 5s
    min_time: 5s
```

`min_time` on the server is a defence against pathologically chatty clients — it's the floor on how fast a client may ping. Match it to your `time` on the client.

## 2 · Bounded retries — safe to retry

The client's retry layer wraps data-path RPCs with a configurable wall-clock window (`rpc.retry_window`, default **60 s**) and exponential backoff (100 ms initial, capped at 1 s). Each attempt gets its own fresh deadline derived from the per-attempt timeout (`timeout_meta` / `timeout_io`); the window bounds the **whole operation** across however many attempts fit within it. On a transient `Unavailable` / `DeadlineExceeded` the client retries quietly; on a logical error (`NotFound`, `PermissionDenied`, `InvalidArgument`) it surfaces immediately. If the window expires before the path recovers, the in-flight syscall returns `EIO` to the caller. Setting `rpc.retry_window: 0` disables retrying entirely (fail-fast, single attempt).

Three classes of RPC each have different retry semantics across a session-id change (i.e. when `Resume` fails and a fresh `Create` allocates a new session):

- **Idempotent reads** (`GetAttr`, `Access`, `Readdir`, `Lookup`, and kin) — safe to retry on any session; the op is a pure observation.
- **Fd ops** (`Read`, `Write`, `Flush`, `Fsync`, `Release`, …) — the fd was allocated in the old session and is dead in the new one; retry stops as soon as the session id changes.
- **Path mutations** (`Mkdir`, `Rmdir`, `Rename`, `Unlink`, …) — replay-unsafe on a new session (the old idempotency cache is gone); retry stops on a session-id change.

**`Write` and other mutations** carry a `request_id` generated once per logical operation, reused across retries. The server keeps a per-session idempotency cache (`DoOnce`) keyed by that id: a retried write that already landed is deduplicated server-side rather than applied twice. This makes retry safe within the same session.

## 3 · Stable file handles — opens survive a short outage

When the client opens a file, the server allocates an fd in a per-session store. The keepalive/session stream reconnects in the background, and the server holds onto a disconnected session's fds for a **grace period** (`server.session.grace_period`, default **60 s**) before reaping them:

- If the client reconnects **within** the grace period, it resumes the existing session and its fds stay valid; reads/writes continue from where they were.
- If the outage **exceeds** the grace period, the server releases the fds. The client then starts a fresh session with a new `Create` and logs that any previously open fds are now invalid.

So an open file handle survives a brief drop, but only up to the grace window. The grace period default (60 s) is aligned with the client's `rpc.retry_window` default (also 60 s) so that a retrying client is likely to find its session still alive. A data-path op in flight during the drop retries within the `rpc.retry_window` budget from §2; if the path doesn't recover in time, that syscall returns `EIO` even though the session may later resume.

## The connection state machine

```mermaid
stateDiagram-v2
  [*] --> Connecting
  Connecting --> Connected: handshake ok
  Connecting --> Failed: dial timeout

  Connected --> Reconnecting: keepalive ACK<br/>missed (~40 s)
  Reconnecting --> Connected: handshake ok<br/>fds reattached
  Reconnecting --> Failed: max retries

  Connected --> Closing: user umount
  Closing --> [*]
  Failed --> [*]

  note right of Connected
    in-flight ops retry
    within rpc.retry_window
    (default 60 s) during
    Reconnecting
  end note
```

While **Reconnecting**, the session stream re-establishes in the background and fds stay valid for up to the grace period. In-flight data-path ops retry within the `rpc.retry_window` budget; if the path doesn't recover in time they return `EIO` even before the state machine lands in **Failed**.

## What the user sees

| Situation                                       | Outward symptom                                                                      |
| ----------------------------------------------- | ------------------------------------------------------------------------------------ |
| Sub-second blip within the retry window         | In-flight op retries and succeeds. No error visible.                                  |
| Blip longer than `rpc.retry_window` (default 60 s) | In-flight ops exhaust the retry window and return `EIO`; the session may still reconnect in the background and fresh ops succeed once it does. Open fds stay valid (within the 60 s grace period). |
| Server reboot, recovery within 60 s grace       | Ops in flight during the drop may return `EIO` if the window expires; the session resumes with fds intact once the server is back. |
| Outage longer than the 60 s grace period        | Server releases the fds. Client starts a fresh session — previously open fds are invalid. New attempts retry; server back → recovery. |
| Server permanently gone (intentional shutdown)  | `EIO` until you `umount` and re-mount somewhere else.                                |

:::tip[Tuning for your network]
The defaults target consumer-internet flakiness (~40 s keepalive detection, 60 s retry window). If your link is reliable LAN, leave them alone. If it's satellite or cellular with bursts of loss, **raise** `rpc.keepalive.timeout` and `rpc.retry_window` so you don't tear down a connection that would have recovered. Set `server.session.grace_period` to the same value or higher so fds outlast the retry window. If you need fail-fast for an automation pipeline, **lower** `keepalive.time`, `keepalive.timeout`, and set `retry_window: 0`.
:::

## What it isn't

- **Not a VPN.** There's no tunnel layer; reconnection re-establishes the same gRPC connection, not a session over a different transport.
- **Not multi-server failover.** A mount targets one server. If that server is gone, you re-mount elsewhere — there's no built-in failover yet.
- **Not write-replay.** A coalesced write that hit the server **and** got an ACK is durable; a coalesced write that the client dropped on the floor during a disconnect is lost. Applications that need durability call `Flush` or `Fsync` — see [Client config — Write Coalescing](../client/config.md#write-coalescing).
