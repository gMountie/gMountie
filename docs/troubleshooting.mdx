# Troubleshooting

**Read top to bottom on first hit, or jump to the symptom.** Most issues fall into four buckets: the mount itself didn't come up, the connection won't establish, files behave wrong inside the mount, or things are slower than they should be.

## Quick triage

```bash
# Server reachable from the client?
nc -zv <server-host> 9449

# Client mounted?
mount | grep gmountie

# Look at the mount log — gmountie mount logs to stderr; run with -v for debug.
gmountie mount -v -c client.yaml /mnt/shared
```

If the server prints `serving on :9449` and `nc` connects but the mount still fails, the issue is auth, volume, or FUSE — keep reading.

## Mount failures

### `fusermount3: command not found` (or `fuse: device not found`)

The client side needs `fuse3` installed and `/dev/fuse` available.

```bash
# Debian / Ubuntu
sudo apt install fuse3

# Verify
ls -l /dev/fuse        # should exist
fusermount3 --version  # should print
```

:::note[Root / `user_allow_other`]
gMountie mounts as the invoking user, not root. If you see `fusermount3: option allow_other only allowed if 'user_allow_other' is set in /etc/fuse.conf`, you don't need that flag — gMountie doesn't pass `allow_other` by default. If a script of yours does, either remove it or set `user_allow_other` in `/etc/fuse.conf`.
:::

### `mount: <path>: file exists` or `transport endpoint is not connected`

A stale mount is still registered at the same path. Unmount it before re-mounting:

```bash
umount /mnt/shared                   # normal
fusermount3 -u /mnt/shared           # FUSE-aware
sudo umount -l /mnt/shared           # lazy — last resort
```

### `mountpoint must be an empty directory`

The directory you're mounting at has content. Either pick an empty path or move the contents:

```bash
ls /mnt/shared                       # must be empty
mkdir -p /mnt/shared                 # create one if missing
```

## Connection errors

### `Unavailable: connection refused`

The server isn't listening where the client is looking.

- Confirm the server process is running: `pgrep -a gmountie`.
- Confirm the server's `address` / `port` (from `server.yaml`) match the `--server` flag the client passes.
- Confirm a firewall isn't blocking the port — `sudo ufw status`, `iptables -L`, cloud SG rules.

### `Unavailable: dial timeout` or sudden `EIO` after a working mount

The TCP path went away — NAT rebind, ISP IP change, server reboot, network hiccup. gMountie's keepalive surfaces this as `Unavailable` within ~40 s by default ([sessions & reconnect](./concepts/sessions-and-reconnect.mdx) explains the timing).

- For a sub-second blip, in-flight ops **retry on a bounded budget (~2 s)** and usually succeed; let it ride. A longer blip exceeds that budget and surfaces as `EIO` on the in-flight op, while the session reconnects in the background and fresh ops succeed.
- If the server actually died, ops return `EIO` on the next syscall. Restart it: the mount auto-recovers, and file handles opened before the blip stay valid **as long as the server comes back within its 30 s session grace period**. After that, the client starts a fresh session and previously open fds are invalid.

:::tip
Tighten or loosen detection with `server.keepalive` and `rpc.keepalive` — see the [server](./server/config.md) and [client](./client/config.md) config pages.
:::

### `Unauthenticated` / `PermissionDenied`

The auth handshake failed.

- Confirm `auth.type: basic` on both sides — it's the only scheme today.
- Confirm `username` / `password` match an entry in the server's `auth.users` list.
- The client always supplies credentials; there is no anonymous mode (the previous `auth: none` was removed).

## Permission and ownership issues

The visible owner of a file depends on the volume's **[mapping mode](./concepts/identity.mdx)** on the server (`squash` / `static` / `system` / `passthrough`) and whether the client is using `--raw-ids`. When something looks wrong, the fastest first move is to switch on `--raw-ids` to see what the server actually thinks.

### Files show up owned by `nobody` (uid 65534) or by the wrong user

The client rewrites `ls -l` based on a `WhoAmI` reply from the server. If that reply doesn't match a file's actual uid/gid, the rewrite falls back and you see the raw value — often `nobody` (65534) on systems with that anonymous account.

Causes, in order of likelihood:

- **Mapping mode and your principal don't match.** In `static` mode, a file owned by `bob` (uid 1002) on the server shows up unrewritten if you authenticated as `alice` — `alice` won't be rewritten *to* `bob`. That's correct: the file isn't yours.
- **`passthrough` with `root_squash`.** Files written by client-root land as `anon_uid` (usually 65534) on the server. Listings of those files show `nobody`. Either turn off root_squash on that volume or write as a non-root user.
- **`system` mode where the user doesn't exist on the server.** The server replies with the anonymous identity; everything shows as `nobody`. Add the user to the server's NSS, or switch the volume to `static` with an explicit entry.

First debugging move:

```bash
gmountie mount … --raw-ids        # see the raw uids the server reports
```

Then cross-reference against the volume's `mapping` block in `server.yaml`.

### `Permission denied` on a write the local user "should" be able to do

The check runs **on the server**, against the **resolved** identity for your volume — not against your client uid. The local view (`ls -l` showing your username after the rewrite) doesn't grant permission; the server's actual file mode and ownership do.

Two common shapes:

- **`squash` mapping** — everyone becomes the configured `uid`/`gid`. If that uid doesn't have write permission on the file, *nobody* mounted on this volume can write it. Either widen the file's permissions or change the mapping so the right principal lands on the right uid.
- **`static` or `system` mapping** — the file is owned by someone other than your resolved identity. `ls -l --raw-ids` shows the real uid; reconcile by adjusting file ownership on the server, the mapping table, or the user's group membership.

When in doubt: `--raw-ids` + the volume's mapping block in `server.yaml`. The combination tells you exactly what identity the server is acting as.

## Performance feels wrong

### "It's slow"

First — **measure**. Cold first reads cross the wire; subsequent reads of the same file (and the same directory) hit the [cache](./concepts/cache.mdx) if it's enabled:

```bash
# Time the same listing twice in a row
time ls /mnt/shared > /dev/null       # cold
time ls /mnt/shared > /dev/null       # warm — should be sub-ms
```

If the warm read isn't fast, the cache may be off. In `client.yaml`:

```yaml
cache:
  enabled: true
```

### Sequential reads are slower than expected on a high-RTT link

The readahead window is sized for ~50 ms RTT by default. On longer links, raise it:

```yaml
rpc:
  readahead_window: 8        # default 4; range 1–64
  readahead_chunk_bytes: 1048576  # 1 MiB — match the server's frame_size_bytes
```

See [Client configuration](./client/config.md) for the full readahead model.

### Many tiny writes saturate the wire

Write coalescing should be batching them — confirm `rpc.write_coalesce_bytes > 0`. The default 1 MiB absorbs typical "append a line, append a line" patterns.

```yaml
rpc:
  write_coalesce_bytes: 1048576   # 1 MiB; 0 disables, max 16 MiB
```

:::warning[Durability after coalescing]
Coalesced writes return optimistically. If your application needs a write **observed by another reader** before continuing, it must `Flush` or close the fd. A buffered write that fails surfaces as `EIO` on the next `Flush` / `Fsync`.
:::

## When the above doesn't help

Capture a verbose log from one mount session and open an issue with it attached:

```bash
gmountie mount -v -c client.yaml /mnt/shared 2> /tmp/gmountie-mount.log
```

Include the server's startup output too, the client OS / kernel (`uname -a`), `fuse3` version, and a one-line description of what you did and what happened.
