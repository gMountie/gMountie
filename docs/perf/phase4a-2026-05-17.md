# Phase 4 / Sub-spec A migration — perf delta vs Phase 3 final

**Date:** 2026-05-17.
**Commit measured:** `562b610` (Task 5 + the Allocate/lock-ops fix).
**Compared against:** `docs/perf/phase3-final-2026-05-15-localhost.txt`.

## TL;DR

The pathfs → fs migration is **observationally equivalent** on the
localhost bench. No single benchmark shows a statistically significant
sec/op change against Phase 3 final (every line is `~` at p > 0.05).
Geomean shifts: +2.72 % sec/op, +2.22 % B/op, essentially unchanged
allocs/op. **Sub-spec A is safe to merge** on the perf axis.

The TCP harness produces a new baseline (no comparable Phase 3 TCP run
exists — F4 added the TCP harness *after* the Phase 3 deltas were
captured against bufconn). See "TCP baseline" below.

the pre-existing EIO flake (documented in `docs/perf/baseline-2026-05-15.md`
and the F3 commit message). F3's mitigation reduced the rate but didn't
eliminate it; here we still see a few failed iterations.

## TCP baseline (new — no Phase 3 comparable)

`task perf:bench:tcp` produced [`phase4a-2026-05-17-tcp.txt`](./phase4a-2026-05-17-tcp.txt).
This is the first run of the real-TCP harness without `tc netem`
shaping, so it establishes a baseline for future TCP-transport
comparisons rather than diffing against Phase 3 (Phase 3's TCP
harness didn't exist yet).

A naive diff against `docs/perf/baseline-2026-05-15-slow30ms.txt`
(Phase 3's bufconn-with-netem run, which `tc qdisc` couldn't actually
shape because bufconn doesn't touch `lo`) shows large apparent
regressions on bulk-I/O benches — but those are explained by "now
we're actually measuring the wire," not by Phase 4A. The proper
comparison is Phase 4A-TCP-no-shape vs Phase 4A-TCP-30ms-shape, which
hasn't been captured here.

Full raw output: [`phase4a-2026-05-17-tcp.txt`](./phase4a-2026-05-17-tcp.txt).
