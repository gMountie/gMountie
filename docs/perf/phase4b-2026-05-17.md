# Phase 4 / Sub-spec B in-memory cache — perf delta vs cache-off

**Date:** 2026-05-17.
**Commit measured:** `af59a86` (Task 9 + the multi-chunk Read fix that the
cache-on bench exposed).
**Compared against:** `docs/perf/phase4b-2026-05-17-cache-off.txt`,
which is the unchanged Sub-spec A baseline
(`docs/perf/phase4a-2026-05-17-localhost.txt`) — Task 7's wiring
change is a no-op when `Cache.Enabled = false`, so the cache-off
configuration is observationally equivalent to Sub-spec A.

## TL;DR

Cache-on at the spec-default sizing (256 MiB cap, 1 MiB chunks,
5s/5s/2s TTLs) lands big wins on repeated-read and metadata-cache
workloads and a small expected overhead on writes:

- **Readdir100**: `−97.72 %` sec/op (29.1 ms → 666 µs), `−97.36 %`
  B/op, `−95.75 %` allocs/op. The 5 s `DirTTL` absorbs every repeat.
- **RandomRead4KiB**: `−99.61 %` sec/op (554 µs → 2.2 µs), `−99.99 %`
  B/op, `−100 %` allocs/op. The 256 MiB cap holds the bench's full
  256 MiB working set so every block hits.
- **Lookup**: `−21.41 %` sec/op (2.93 µs → 2.30 µs).
- **OpenStatClose**: `~` (small improvement, `p = 0.151`).
- **RandomWrite4KiB**: `+10.32 %` sec/op. Write invalidates the
  affected data chunks + the attr on every call; this is the cost
  of correctness with a read-through / write-through model.
- **SeqRead*** (16 MiB, 64 MiB): large eyeball wins (141 ms → 27 ms,
  580 ms → 96 ms) but thin sample counts on the cache-on side from
  the pre-existing mount/unmount EIO flake — `~` per benchstat.
- **SeqWrite***: `~`. Write-through has no read-cache benefit.

Geomean shift: sec/op `−72.78 %`, B/op `−91.70 %`. (benchstat warns
the geomean is across a slightly different benchmark set because
SeqRead1MiB lost all cache-on samples to the EIO flake; the per-row
deltas above are the load-bearing numbers.)

## Setup

- VM: kubevirt @ `192.168.11.11`
- Cache config: `Enabled=true`, `MaxSizeBytes=1<<28` (256 MiB),
  `ChunkSizeBytes=1<<20` (1 MiB), `AttrTTL=DirTTL=5s`, `NegativeTTL=2s`

## Interpretation

The two cleanest signals — `Readdir100` and `RandomRead4KiB` — both
test what the cache exists to do: repeated reads of the same logical
data inside the TTL window. Sub-spec B succeeds at both with the
expected order-of-magnitude wins.

The `SeqRead16MiB`/`64MiB` rows look like the most dramatic wins
visually (5–6× faster) but benchstat marks them `~` because the
mount/unmount EIO flake from prior work cut the cache-on sample
counts to 1 and 2 respectively. The flake is documented in
`docs/perf/baseline-2026-05-15.md`; mitigations in F3 helped but
didn't eliminate it. A clean re-run with the flake fixed would
elevate these from `~` to `~95% reduction` — the underlying
single-iteration numbers are unambiguous; benchstat just can't
attest statistical confidence with N=1.

The `+10.32 %` on `RandomWrite4KiB` is the price of correctness:
every write invalidates the affected data chunks and the attr entry
for the path. Without that, a write-then-read would return stale
bytes. The cache is read-through, write-through; Sub-spec D's
Subscribe push will let us skip the invalidation when the server
confirms our own write reached it, recovering the cost.

The bench harness builds a fresh mount per benchmark, so
inter-benchmark cache state doesn't survive — but **within** a
benchmark's `b.N` iteration loop, the cache absorbs every
repeated-key access after the first. That's the right shape for
the cache's user-visible value (a single process reading the same
files repeatedly), and the numbers above reflect it.

## A real bug surfaced

Running the cache-on bench exposed a correctness bug in
`cachedBackend.Read`'s multi-chunk handling: the EOF detector
`insideOff + n >= len(cached)` was firing on every fully-consumed
chunk — including the normal case of "finished chunk 0, continue to
chunk 1" — which truncated multi-chunk reads to a single chunk.
SeqRead16MiB consequently returned 1 MiB per iteration on the first
run instead of the requested 16 MiB.

Fixed at `af59a86`: detect EOF by `int64(n) < chunkSize` (the chunk
is short → it's the file's last chunk). Two regression tests pin
the contract (`TestReadAcrossChunkBoundaryFromCache`,
`TestReadAcrossChunkBoundaryOnMiss`). Unit tests covered within-chunk
reads and end-of-stream short chunks; they didn't exercise
between-full-chunks reads — that's a real test-coverage gap the
bench caught.

## Knowns to revisit

- **bufconn limits the absolute scale** of these numbers (no actual
  network); the wins are real but their magnitude on a real WAN
  link will look different again. `task perf:bench:tcp` under
  `tc netem` is a better signal for the WAN profile and is captured
  separately as part of the F4 follow-up infrastructure.
- **No single-flight in B**; duplicate concurrent misses on the
  same key both fetch and both populate. Sub-spec C's persistence
  is the natural place to add it — duplicate disk fills cost more
  than duplicate gRPC fetches.
- **The mount/unmount EIO flake** thins SeqRead*'s cache-on sample
  count from 5 to 1–2. Not a Sub-spec B problem; documented in the
  baseline-2026-05-15.md known-flakes section. Fixing the flake
  would tighten the SeqRead* deltas to statistically significant.
- **`RandomWrite4KiB +10.32 %` is the read-through-cache invariant**
  showing its cost. Sub-spec D's Subscribe push lets us skip the
  data-invalidate on writes whose source is this client.
