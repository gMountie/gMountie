The harness runs everything in-process — server + client share the same Go
binary and talk over a `bufconn` listener. The only thing being shaped in the
"slow30ms" profile is the loopback `lo` interface for kernel-FUSE syscall
traffic (i.e. the `/dev/fuse` user→kernel boundary still uses host memory).
Because the gRPC channel is bufconn rather than a real socket, the 30 ms
profile primarily exercises the FUSE layer; the gRPC client/server itself is
not subject to the netem qdisc. Future work that moves the harness to a real
TCP transport will tighten this signal.

## Pre-Phase-3 state

Relevant defaults that Phase 3 will revisit, captured here so a future reader
can correlate deltas to specific changes:

- **Compression:** Snappy is the global codec for all gRPC frames
  (`pkg/server/grpc/snappy`). No per-RPC opt-out, no content-type tagging.
- **Read/Write transport:** unary RPCs only — `RpcFile.Read` / `RpcFile.Write`
  one request, one response per chunk. No streaming, no batching.
- **FUSE settings:** plain `pathfs.NewLoopbackFileSystem` with go-fuse
  defaults — no `max_read`, no `max_write`, no writeback cache, no large_read.
- **Retry policy:** `avast/retry-go` on the client with default backoff.
- **Allocations:** read/write paths allocate per-call; no buffer pool.

## Known flakes (treat as inputs to Phase 3 review, not blockers)

Several benchmarks emit intermittent FUSE `EIO` between iterations under the
`-count=N` loop. The pattern looks like a real bug in the server's
mount/unmount-under-rapid-cycle path — each benchmark gets a fresh
`AppTestingContext` (server + mount), and the EIO surfaces on the *open* path
inside an otherwise-clean benchmark. Affected so far:

- `BenchmarkReaddir100` — `readdirent: input/output error` on second / fourth
  COUNT iter (about 30–40% of attempts).
- `BenchmarkSeqWrite1MiB` and `BenchmarkSeqWrite16MiB` — `create: input/output
  error` on the `os.Create` call early in some iterations (about 20% of
  attempts on slow30ms; the 1 MiB Write produced no usable slow30ms samples).
- `BenchmarkRandomRead4KiB` failed once on the localhost run and passed
  cleanly when re-run in isolation, so it's flakiest of the lot.

`benchstat` ignores the `--- FAIL:` lines, so the baseline files are
parseable. But for Task 10 we'll want either: (a) a retry-on-EIO wrapper
around the bench bodies, or (b) a root-cause fix in the FUSE
mount/unmount path. The behaviour predates Phase 3 work; capturing it here
so the streaming changes in Tasks 2–3 can be evaluated for whether they
incidentally affect it.

## bufconn limitation

The test harness is **in-process**: server + client run inside one Go binary
and talk over a `bufconn` listener. Two consequences for the `slow30ms`
profile:

- `tc qdisc … netem delay 30ms dev lo` does not affect the gRPC transport,
  because bufconn never touches the `lo` interface. It only adds latency
  on syscalls that round-trip through `lo` (which the FUSE↔kernel path also
  does not — `/dev/fuse` is a character device, not a network socket).
- As a result, the `slow30ms` numbers are largely indistinguishable from
  `localhost` (see the side-by-side diff in the Phase 3 task 10 deltas).

The profile is captured anyway so Task 10 can re-run the exact same
procedure and produce a comparable file. A future task should switch the
harness to a real TCP listener so the latency profile is actually
exercised — tracked as a follow-up out of Phase 3 scope.

## How to reproduce

The repo's `scripts/start-slow-loopback.sh` is stale (uses `tc qdisc change`
without a prior `add`; the args are also hardcoded to 10ms / 1000Mbit and
don't honour command-line input). Use `tc` directly:

```bash
ssh ubuntu@192.168.11.11
cd ~/gMountie && git checkout <bench-commit>
task perf:install            # one-time

task perf:bench OUT=/tmp/localhost.txt

sudo tc qdisc add dev lo root netem delay 30ms
task perf:bench OUT=/tmp/slow30ms.txt COUNT=3 BENCHTIME=20s
sudo tc qdisc del dev lo root

task perf:diff BEFORE=docs/perf/baseline-2026-05-15-localhost.txt AFTER=/tmp/localhost.txt
```
